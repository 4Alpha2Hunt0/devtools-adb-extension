# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo contains **two unrelated projects** that happen to share a git history. Treat them as independent — changes to one should never touch the other's files.

1. **`extension/`, `dist/`, `Makefile`, `template-*.json`** (root level) — the original project: the Firefox DevTools ADB Extension, which packages platform-specific `adb` binaries into signed `.xpi` files so Firefox DevTools can talk to Android/GeckoView devices over USB.
2. **`obsidian-brain/`** — a personal Obsidian vault + companion tooling (plugin and a Node.js inbox watcher), scaffolded inside this repo because the session that created it (see `obsidian-brain/README.md`) didn't have permission to create a new GitHub repo. It does not touch the extension's build in any way.

## Part 1: ADB Extension (root)

### Structure

- `extension/adb.json` — maps `platform.system()` (`Linux`, `Darwin`, `WINNT`) and CPU arch (`x86`, `x86_64`) to the relative binary path(s) to bundle.
- `extension/<arch>/` (`linux`, `linux64`, `mac64`, `win32`) — the actual vendored `adb` binaries (plus Windows DLLs) and their upstream `LICENSE`/`README`. These are prebuilt Android Platform Tools binaries, not built from source here.
- `extension/template-manifest.json` — WebExtension manifest template with `@@ARCH@@`, `@@VERSION@@`, `@@UPDATE_URL@@` placeholders.
- `template-update.json` (root) — WebExtension update manifest template with `@@VERSION@@`/`@@UPDATE_LINK@@` placeholders.
- `dist/` — build output (gitignored except for its own `README.md`); regenerated by `make package`.

### Build commands

```bash
make package   # clean dist/, then build one .xpi + update.json per arch into dist/<arch>/
make clean     # remove dist/<arch>/ folders
```

For each arch, `make package` generates a temporary `extension/manifest.json` from `template-manifest.json`, zips it with that arch's binaries and `adb.json` into `dist/<arch>/adb-extension-<version>-<arch>.xpi`, deletes the temporary manifest, then writes `dist/<arch>/update.json` from `template-update.json`. There is no lint/test suite for this half of the repo — it's packaging of vendored binaries, not application code.

### Key convention: per-arch version suffix

`Makefile`'s `VERSION` variable must have **exactly three parts** (e.g. `0.0.8`). `build-xpis` loops over `ARCHS = linux linux64 mac64 win32` and appends a fourth, auto-incrementing index (`.0`, `.1`, `.2`, `.3`) per arch — so one `VERSION` bump produces four distinct four-part versions, one per platform. This is required by AMO's version-ordering rules during release (see below); never hand-edit a four-part version into the Makefile.

### Release process (manual, from README.md)

1. Bump `VERSION` in `Makefile` and commit.
2. Run `make package`; verify `dist/<arch>/adb-extension-<version>-<arch>.xpi` + `update.json` for all four arches.
3. Upload each `.xpi` to AMO as an **unlisted** version, strictly in arch order (`linux`, `linux64`, `mac64`, `win32`) since their auto-generated versions must ascend in that order.
4. Download the AMO-signed `.xpi`s and rename each back to the original `adb-extension-<version>-<arch>.xpi` (AMO renames them on signing).
5. Upload the signed `.xpi`s plus their `update.json` to the FTP server, both as the versioned filename and as an `adb-extension-latest-<arch>.xpi` copy (same file, verify via `sha256sum`).

## Part 2: obsidian-brain

Three independent pieces sharing one vault. None of them build or test the ADB extension.

### `obsidian-brain/vault/`
The actual Obsidian vault: `Home.md` entry point, `Projects/`, `Tools/` (includes the generated `Dashboard.md`), `Templates/` (used by the plugin when creating notes), and `.obsidian/` config. `Daily/` and `Inbox/`/`Attachments/` are created automatically at runtime, not checked in.

### `obsidian-brain/plugin/` — Obsidian plugin (TypeScript)
Commands, all implemented in the single `main.ts`:
- **Log tool usage** — bumps a tool note's `times_used`/`first_used`/`last_used` frontmatter and appends linked entries to both the tool note (`## Usage Log`) and today's daily note (`## Tool Log`), creating either note from its template if missing.
- **New tool reference note** — catalogs a tool without counting a use.
- **New project note** — creates a note under `Projects/` from the project template.
- **Refresh tools dashboard** — rewrites `Tools/Dashboard.md` from every note's frontmatter in `Tools/`, sorted by usage count. This note is regenerated wholesale on each run — never hand-edit it.

Folder names (`Daily`, `Tools`, `Projects`, `Templates`) are user-configurable via the plugin's settings tab; don't hardcode them when adding features — read from `this.settings`.

```bash
cd obsidian-brain/plugin
npm install
npm run build       # tsc -noEmit -skipLibCheck (typecheck only) + esbuild production bundle -> main.js
npm run dev          # esbuild watch mode
npm run typecheck    # tsc -noEmit -skipLibCheck only
```
To load it into the vault: copy `manifest.json` and the built `main.js` into `vault/.obsidian/plugins/obsidian-brain/` (the vault already lists the plugin as enabled in `community-plugins.json`).

### `obsidian-brain/inbox-watcher/` — standalone Node.js tool (no Obsidian API)
Watches the vault's `Inbox/` folder via `chokidar` and, per dropped file, runs a fixed pipeline across four modules in `src/`:
1. `watch.js` — entry point; wires the watcher and calls the pipeline below per new file.
2. `extract.js` — pulls text out of the file (`.md`/`.txt`/`.csv`/`.json`/`.log` read directly, `.pdf` via `pdf-parse`, `.docx` via `mammoth`; images are passed through for direct multimodal classification).
3. `classify.js` — sends the extracted content to Claude (`@anthropic-ai/sdk`) and parses back a title, summary, tags, and category (`tool`/`project`/`note`).
4. `vaultWriter.js` — files a new note into the matching vault folder and archives the original into `Attachments/` (never overwrites — appends a numeric suffix on name collision).

`config.js` loads and validates `.env` (`ANTHROPIC_API_KEY`, `VAULT_PATH`, `INBOX_DIR`, `ATTACHMENTS_DIR`, `MODEL`) and throws immediately if a required var is missing.

Tool notes it writes use the **same frontmatter schema** as the plugin (`times_used`, `first_used`, `last_used`), so the plugin's "Refresh tools dashboard" command picks up inbox-filed tools alongside manually-logged ones — keep both in sync if you change the schema in one place.

On any failure (bad key, rate limit, unsupported format, network error) the file is logged and **left in the inbox untouched** for retry on next restart — don't change this to auto-delete or auto-retry without discussion, it's a deliberate no-data-loss guarantee.

```bash
cd obsidian-brain/inbox-watcher
npm install
cp .env.example .env   # then fill in ANTHROPIC_API_KEY and VAULT_PATH
npm start               # runs src/watch.js, stays running
npm test                # runs test/run-test.js against a mocked Claude client — no API key/network needed
```

Running a single test: `test/run-test.js` is a plain Node script (not a test-framework runner), so there's no built-in filter flag — run `node test/run-test.js` directly and narrow by temporarily commenting out cases, or read the file to find its exported/invoked scenario names.

Every dropped file triggers one real, billed Claude API call (content truncated to ~20k chars); there's no batching or caching, so testing changes against the live watcher (rather than the mocked `npm test` suite) has a real cost.
